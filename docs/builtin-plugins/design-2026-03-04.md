# 内置插件与用户插件管理设计

## Part 1: 内置插件管理架构

### 需求

1. 系统内置 100 个常见插件（预装在镜像中）
2. 用户可以安装自定义插件，安装方式有两种：
   - 通过 ComfyUI Manager 安装，持久化到 `/mnt/auto/custom_nodes/`
   - 通过 git clone 安装，持久化到 `/mnt/auto/custom_nodes/`
3. 当内置插件与用户自定义插件同名时，用户插件优先
4. **不污染用户 NAS**（内置插件不应出现在用户 NAS 中）
5. **Manager 必须安装到 NAS**（持久化）

---

### 背景

以下约束来自 ComfyUI 和 ComfyUI-Manager 源码分析。

#### 1. ComfyUI 在启动时会加载 extra_model_paths.yaml 配置的模型和插件

ComfyUI 启动时在 `main.py:27-29` 加载 `extra_model_paths.yaml`，通过 `utils/extra_config.py` 解析。解析逻辑：

```python
# utils/extra_config.py（简化）
for section_name in config:
    conf = config[section_name]
    base_path = conf.pop("base_path", None)
    is_default = conf.pop("is_default", False)
    for folder_name in conf:                          # 如 "custom_nodes", "checkpoints"
        full_path = os.path.join(base_path, conf[folder_name])
        folder_paths.add_model_folder_path(folder_name, full_path, is_default)
```

`add_model_folder_path` 的行为（`folder_paths.py:281-295`）：
- `is_default: true` → `paths.insert(0, path)`，插入到列表头部。
- `is_default: false`（默认）→ `paths.append(path)`，追加到列表尾部。

#### 2. ComfyUI 默认将 `comfyui/custom_nodes` 作为插件搜索路径的第一项

ComfyUI 在 `folder_paths.py:43` 初始化：

```python
folder_names_and_paths["custom_nodes"] = ([os.path.join(base_path, "custom_nodes")], set())
```

即 `comfyui/custom_nodes` 天然就是 `folder_paths[0]`。由于我们的架构中 `comfyui/custom_nodes` 是指向 NAS 的软链接，**NAS 无需额外配置就已经是 `[0]`**。

#### 3. ComfyUI Manager 强制将插件安装到 `folder_paths[0]`

Manager 强制安装到 `folder_paths.get_folder_paths("custom_nodes")[0]`（`manager_core.py:62-71`）。因为 NAS 天然是 `[0]`，Manager 安装的插件直接写入 NAS，立即持久化。

#### 4. ComfyUI 按路径列表顺序加载插件，后加载的同名节点类会覆盖先加载的

ComfyUI 按 `folder_paths` 列表顺序依次加载各路径下的插件（`nodes.py:2232-2247`）。同名节点类（NODE_CLASS_MAPPINGS key）直接覆盖，**后加载的赢**（`nodes.py:2176-2178`）。

#### 5. Manager 安装目标与用户插件优先级之间存在内在矛盾

| 目标 | 要求 |
|---|---|
| Manager 安装到 NAS | NAS 必须是 `folder_paths[0]` |
| 用户插件覆盖内置插件 | NAS 必须**后加载**（更高下标） |

NAS 不可能同时既是 `[0]` 又排在后面。所有方案都在围绕这个矛盾做取舍。

#### 6. 同名插件出现在多个路径时，ComfyUI 会双重加载导致运行异常

如果同一个插件目录名出现在两个路径中（如 NAS 有 `PluginX`，另一个路径也有 `PluginX`），ComfyUI 会**两个都加载**（`sys_module_name` 基于完整路径，不会去重，参见 `nodes.py:2132-2145`）。双重加载可能导致：后台线程重复启动、Web 路由冲突、全局状态异常。因此**必须有排除逻辑**，确保同名插件只在一个路径中出现。

#### 7. Linux 文件系统大小写敏感，排除逻辑须忽略大小写进行匹配

Linux 文件系统大小写敏感。`ComfyUI-Plugin` 和 `comfyui-plugin` 是不同的目录，但通常是同一个插件（用户手动 clone 时可能改名）。排除逻辑需要**忽略大小写**进行匹配。

### 方案对比

#### 方案 A：Merge View（合并视图）

**机制：** 破坏原有 `comfyui/custom_nodes -> NAS` 软链接，将 `comfyui/custom_nodes` 改为实体目录，里面只放内置插件的软链接（排除 NAS 已有的）。通过 `extra_model_paths.yaml` 将 NAS 设为 `is_default: true`，使其成为 `folder_paths[0]`。

```
folder_paths = [
  [0] /mnt/auto/custom_nodes/           ← NAS (is_default: true)，Manager 安装目标
  [1] /root/comfyui/custom_nodes/       ← 合并视图（仅含不冲突的内置插件软链接）
]
```

| 优点 | 缺点 |
|------|------|
| 逻辑闭环，Manager 正常工作 | **破坏原有软链接架构**，需修改 `snapshot_loader.py` |
| 不污染 NAS | 系统侵入性较高（改变了 custom_nodes 的本质） |
| 排除逻辑解决同名插件冲突 | 同名节点类冲突仍存在（内置后加载覆盖用户） |

#### 方案 B：注入 NAS

**机制：** 保留原有软链接。在启动时将内置插件以软链接形式注入到用户 NAS 目录中。通过"是否为软链接"区分内置与用户插件。

```
/mnt/auto/custom_nodes/
  ├── UserPlugin/               ← 用户（实体目录）
  ├── BuiltinPluginA → /root/built-in/.../BuiltinPluginA  ← 内置（软链接）
  └── ...
```

| 优点 | 缺点 |
|------|------|
| 架构最简单，无需额外路径配置 | **严重污染用户 NAS**（用户看到 100 个不是自己装的目录）|
| 自愈能力强（软链接被删下次启动重建） | Manager 显示全部插件为"已安装" |
| 保留原有软链接 | 用户"卸载"内置插件无效（重启重建） |

**结论：已否决。** 不可接受的 NAS 污染。

#### 方案 C：Shadow Directory（影子目录）⬅ 采用

**机制：** 保留原有软链接 `comfyui/custom_nodes -> NAS`。在容器内维护一个影子目录 `built-in/custom_nodes_shadow/`，仅包含"NAS 中不存在的内置插件"的软链接。通过 `extra_model_paths.yaml` 将 Shadow 追加到 `folder_paths` 末尾。

```
folder_paths = [
  [0] /root/comfyui/custom_nodes       ← 默认值 = NAS（软链接），Manager 安装目标
  [1] /root/built-in/custom_nodes_shadow/  ← 影子目录（仅非冲突内置插件，通过 extra_model_paths 追加）
]
```

| 优点 | 缺点 |
|------|------|
| **不污染 NAS** | 同名节点类冲突仍存在（内置后加载覆盖用户），但概率极低 |
| **保留原有软链接架构**，无需修改 `snapshot_loader.py` | 需要维护影子目录（逻辑简单） |
| Manager 正常安装到 NAS（天然 `[0]`，无需配置） | |
| 排除逻辑解决同名插件冲突 | |
| **extra_model_paths.yaml 配置最少**（只加一个 section）| |

#### 方案 D：Monkey Patch Manager

**机制：** 让内置插件先加载（`[0]`），NAS 后加载（`[1]`），天然实现"用户覆盖内置"。通过在 built-in 中放一个微型插件，运行时修改 Manager 的 `default_custom_nodes_path` 全局变量，强制 Manager 安装到 NAS。

```
folder_paths = [
  [0] /root/built-in/custom_nodes/   ← 内置（先加载）
  [1] /mnt/auto/custom_nodes/        ← NAS（后加载，用户覆盖内置）
]

+ 补丁插件强制 Manager 安装到 [1]
```

| 优点 | 缺点 |
|------|------|
| 完美解决同名节点类覆盖问题 | **依赖 Manager 内部变量名** `default_custom_nodes_path`，极度脆弱 |
| 用户插件天然覆盖内置 | Manager 升级可能导致补丁失效 |
| | **仍需排除逻辑**（防止同名插件双重加载） |
| | 增加了维护成本（每次 Manager 升级需回归测试） |

**结论：已否决。** 工程脆弱性不可接受，且并未减少排除逻辑的需要。

#### 方案 E：延迟软链接

**机制：** 启动时将 `comfyui/custom_nodes` 设为空实体目录，ComfyUI 加载时跳过。通过 `extra_model_paths.yaml` 依次加载 built-in 和 NAS（NAS 后加载覆盖内置）。加载完成后，异步将 `comfyui/custom_nodes` 切换为指向 NAS 的软链接，使 Manager 后续安装写入 NAS。

```
加载阶段：[0] comfyui/custom_nodes(空) → [1] built-in → [2] NAS(后加载覆盖)
运行阶段：comfyui/custom_nodes → NAS (软链接，Manager 安装目标)
```

| 优点 | 缺点 |
|------|------|
| 完美解决覆盖优先级 | **ComfyUI 重启时失效**（重启后软链接已存在，回到旧状态） |
| 架构巧妙 | 切换时刻存在文件系统竞态风险 |
| | 依赖启动时序，脆弱 |

**结论：已否决。** ComfyUI 每次通过 Manager 重启后方案失效，不具备工程可靠性。

### 最终方案：Shadow Directory（方案 C）

#### 选择理由

1. **不污染 NAS**：用户 NAS 保持纯净。
2. **架构稳定**：保留 `comfyui/custom_nodes -> NAS` 原有软链接，不修改 `snapshot_loader.py`。
3. **Manager 兼容**：NAS 天然是 `folder_paths[0]`（ComfyUI 默认初始化），无需额外配置，Manager 安装直接写入 NAS。
4. **冲突处理**：通过大小写不敏感的排除逻辑，确保同名插件只在 NAS 中加载。
5. **配置最简**：`extra_model_paths.yaml` 只需新增一个 section，将 Shadow 追加到路径列表。
6. **可接受的边缘风险**：不同插件注册同名节点类时，Shadow 后加载会覆盖用户版。但 ComfyUI 社区中插件作者通常为节点类加前缀，此场景在实践中极少发生。

#### 目录结构

```
镜像层（只读）：
  /root/built-in/custom_nodes/          ← 100 个内置插件（原始文件）

运行时影子目录（容器内，临时）：
  /root/built-in/custom_nodes_shadow/   ← 动态生成的软链接集合
    ├── comfyui_controlnet_aux → ../custom_nodes/comfyui_controlnet_aux
    └── （NAS 有 PluginX，则此处无 PluginX 的软链接）

用户 NAS（持久化）：
  /mnt/auto/custom_nodes/               ← 用户安装的插件
    ├── PluginX/
    └── ...

ComfyUI 目录：
  /root/comfyui/custom_nodes → /mnt/auto/custom_nodes  (原有软链接，保持不变)
```

#### 路径配置 (extra_model_paths.yaml)

NAS 无需配置（`comfyui/custom_nodes` 天然是 `folder_paths[0]`）。只需追加 Shadow 目录：

```yaml
funart_builtin_custom_nodes:
    base_path: /root/built-in
    custom_nodes: custom_nodes_shadow/
```

最终 `folder_paths["custom_nodes"]` 的值：

```python
[
  "/root/comfyui/custom_nodes",              # [0] 默认值 = NAS (软链接)，Manager 安装目标
  "/root/built-in/custom_nodes_shadow",      # [1] 追加，内置插件兜底
]
```

#### 启动脚本逻辑 (builtin_custom_nodes.py)

每次 ComfyUI 进程启动前执行：

1. **清空** Shadow 目录（若存在则删除重建，保证状态最新）。
2. **扫描 NAS**，获取用户已安装插件列表（**转小写集合，忽略大小写**）。
3. **遍历 Built-in**：
   - 如果插件名（小写）在 NAS 集合中 → **跳过**（不创建软链接）。
   - 否则 → 在 Shadow 中创建指向 Built-in 对应插件的软链接。
4. **写入** `extra_model_paths.yaml`（追加 `funart_builtin_custom_nodes` section）。

#### 涉及文件

| 文件 | 变更类型 | 说明 |
|------|---------|------|
| `src/code/agent/services/custom_nodes/builtin_custom_nodes.py` | 新建 | 维护 Shadow 目录 + 配置 yaml |
| `src/code/agent/services/management_service.py` | 修改 | 启动前调用 `setup_builtin_custom_nodes()` |
| `src/code/agent/Dockerfile` | 修改 | 从 comfyui 镜像拷贝插件到 built-in 目录 |
| `src/code/comfyui/Dockerfile` | **无需修改** | 插件继续安装到 `comfyui/custom_nodes/` |
| `src/code/comfyui/Makefile` | 修改 | `upload-base` 不再上传 custom_nodes 到 OSS |
| `src/code/agent/services/workspace/snapshot_loader.py` | **无需修改** | 保持原有 NAS 软链接逻辑 |

### Dockerfile 变更说明

#### 职责拆分

| 镜像 | 职责 | custom_nodes 位置 |
|------|------|-------------------|
| `comfyui/Dockerfile` | 构建 ComfyUI 基础环境，安装 100 个内置插件 | `comfyui/custom_nodes/`（不变）|
| `agent/Dockerfile` | 构建运行时镜像，将内置插件复制到 built-in 目录 | `/root/built-in/custom_nodes/`（新增）|

#### agent/Dockerfile 变更

通过多阶段构建，从 comfyui 镜像中提取插件到 built-in 目录：

```dockerfile
ARG COMFYUI_IMAGE=comfyui:v0.3.77-beta
FROM ${COMFYUI_IMAGE} AS comfyui_source

FROM python:3.10.16-slim
# ... 现有 agent 构建逻辑不变 ...

ENV BUILTIN_NODES_DIR="/root/built-in/custom_nodes"

# 从 comfyui 镜像拷贝内置插件到 built-in 目录
COPY --from=comfyui_source /root/comfyui/custom_nodes ${BUILTIN_NODES_DIR}
```

#### upload-base 的变化

**当前行为：** `make upload-base` 将 comfyui 镜像中的 `custom_nodes` 上传到 OSS，作为**用户 NAS 的初始内容**。用户首次启动时，这 100 个插件会被下载到 NAS 中。

**新方案下的变化：** 内置插件已内嵌在 agent 镜像的 `built-in/` 中，不再需要写入用户 NAS。`upload-base` 应不再上传 `custom_nodes`，或上传一个空目录，让用户 NAS 初始为空。

```makefile
# Makefile 修改：移除 custom_nodes 上传
upload-base:
    # 上传 models 和 venv（保持不变）
    ossutil cp -r ./tmp/models oss://...
    ossutil cp ./tmp/venv.tar.zst oss://...
    ossutil cp ./tmp/comfyui.tar.zst oss://...
    # 删除：ossutil cp -r ./tmp/custom_nodes oss://...（不再上传）
```

> **注意：** 若历史快照中已有 custom_nodes 内容在 OSS，用户首次启动时仍会被下载到 NAS。这些插件将成为用户的"已安装插件"，Shadow 目录会自动排除它们，不会双重加载。行为符合预期。

## Part 2: 内置插件列表筛选机制

### 背景

内置的 100 个插件并非手动拍脑袋选出，而是根据 GitHub star 数自动筛选，确保选出的插件具有广泛社区认可度。筛选结果以 JSON 文件形式存储在 `src/code/comfyui/custom_nodes_config/` 目录中，作为 `comfyui/Dockerfile` 安装插件的依据。

### 数据来源

| 数据 | URL |
|------|-----|
| 插件 Star 数 | `https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/github-stats.json` |
| 插件完整列表 | `https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/custom-node-list.json` |

**github-stats.json 格式（节选）：**
```json
{
  "https://github.com/ltdrdata/ComfyUI-Manager": {
    "stars": 12368,
    "last_update": "2026-01-01"
  }
}
```

**custom-node-list.json 格式（节选）：**
```json
{
  "custom_nodes": [
    {
      "title": "ComfyUI-Manager",
      "reference": "https://github.com/ltdrdata/ComfyUI-Manager",
      "install_type": "git-clone",
      "description": "..."
    }
  ]
}
```

### 筛选流程

```
custom-node-list.json   github-stats.json
         │                     │
         └──────── 合并 ────────┘
                  （以 repository URL 为 key）
                       │
                   按 stars 降序排序
                       │
              排除 excluded_custom_nodes.json 中的插件
              （匹配规则：repository URL 完全匹配）
                       │
                   取前 N 个
                       │
        写入 custom_nodes_topn_YYYY-MM-DD.json
```

### 排除列表

`src/code/comfyui/custom_nodes_config/excluded_custom_nodes.json` 存储了**不应被自动选入**的插件（例如资源需求过高、与平台不兼容等）。每次生成 top N 列表时，会从候选集中移除这些插件。

排除列表格式示例：
```json
{
  "custom_nodes": [
    {
      "name": "EasyAnimate",
      "reason": "模型过大，不适合平台默认安装"
    }
  ]
}
```

### 输出文件

每次执行筛选命令都生成一个新文件，文件名包含执行日期，避免覆盖历史快照：

```
src/code/comfyui/custom_nodes_config/
  ├── excluded_custom_nodes.json         ← 排除列表（手动维护）
  ├── custom_nodes_topn_2026-03-04.json  ← 某次生成的 top N 列表
  ├── custom_nodes_topn_2026-03-10.json  ← 另一次生成的 top N 列表
  └── custom_nodes.json                  ← 最终确认使用的列表（手动选择并重命名）
```

> **人工审核环节**：`custom_nodes_topn_*.json` 是**候选列表**，需人工检视后选择一个重命名为 `custom_nodes.json`（或合并内容），再触发 `comfyui/Dockerfile` 重新构建。这确保了自动化效率与人工把控的平衡。

### 筛选脚本

脚本路径：`src/code/comfyui/custom_nodes_config/get_topn.py`

```bash
# 用法
python get_topn.py --top 100
python get_topn.py --top 50 --output-dir /path/to/output
```

脚本逻辑：
1. 从 GitHub raw URL 下载 `github-stats.json` 和 `custom-node-list.json`。
2. 合并数据，以 `reference` URL 为 key 关联 star 数。
3. 按 star 数降序排序。
4. 读取 `excluded_custom_nodes.json`，过滤排除项（匹配 repository URL）。
5. 取前 N 个。
6. 写入 `custom_nodes_topn_YYYY-MM-DD.json`（`YYYY-MM-DD` 为执行日期）。

输出文件格式（与现有 `custom_nodes.json` 一致）：
```json
{
  "metadata": {
    "generated_at": "2026-03-04",
    "top_n": 100,
    "total": 100,
    "source_stats_url": "https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/github-stats.json",
    "source_list_url": "https://raw.githubusercontent.com/Comfy-Org/ComfyUI-Manager/main/custom-node-list.json",
    "excluded_count": 1
  },
  "custom_nodes": [
    {
      "name": "ComfyUI-Manager",
      "repository": "https://github.com/ltdrdata/ComfyUI-Manager",
      "stars": 12368,
      "description": "..."
    }
  ]
}
```
