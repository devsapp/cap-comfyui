# 多 ComfyUI 版本并行构建设计（v0.3.77 + v0.16.4）

**日期**：2026-05-18
**状态**：草稿（待 review）
**配套文档**：测试、升级与回退方案见 [`./testing-2026-05-19.md`](./testing-2026-05-19.md)

---

## 摘要（TL;DR）

为支持新版本 ComfyUI v0.16.4 的多租部署，本提案在**不破坏 v0.3.77 存量**的前提下，把镜像构建参数化、把运行时按版本隔离 OSS/NAS 路径。**多租插件代码本身一行不改**——经源码级调研已确认 v0.16.4 的核心调用面与 v0.3.77 完全兼容，monkey-patch 可直接复用。

主要改动集中在三处：

1. **镜像构建**：`src/code/comfyui/` 拆出 `shared/Dockerfile.template` + `v0.3.77/` + `v0.16.4/` 子目录，通过 `COMFYUI_VERSION` ARG 参数化
2. **Agent 运行时**：新增 `COMFYUI_VERSION` 环境变量（构建期写入），快照路径与 OSS 上传路径自动按版本前缀隔离
3. **构建脚本**：顶层 `Makefile` 新增版本矩阵目标 `build-comfyui-v0.x.x`，原有 `make build-comfyui` 默认仍指向 v0.3.77（零行为变更）

不在本提案范围：第三方插件在 v0.16.4 上的实战兼容性验证、ComfyUI 官方 Asset 系统与多租 user_id 的整合（见「开放问题」）。

---

## 1. 背景

### 1.1 现状

代码库当前锁定 ComfyUI **v0.3.77**：

- `src/code/comfyui/Dockerfile:12` 硬编码 `git checkout "v0.3.77"`
- `src/code/comfyui/Makefile:6` 硬编码 OSS 基础目录 `base/comfyui/v0.3.77-gamma`
- `src/code/comfyui/custom_nodes_config/custom_nodes.json` 是该版本对应的内置插件清单
- 多租能力靠 `src/code/comfyui/custom_nodes/FunArt-ComfyUI-Multi-User/` 的 4 个 monkey-patch 实现（`folder_paths` / `execution.PromptExecutor` / `comfy_execution.caching.CacheKeySetInputSignature` / `server.PromptServer`）
- 用户工作空间快照存在 NAS `${MNT_DIR}/snapshots/<dev|prod>-<ts>/`，里面的 `venv.tar.zst` 与 `comfyui.tar.zst` 与 ComfyUI 版本紧耦合

### 1.2 需求

业务侧需要将 ComfyUI 升级到 **v0.16.4**（跨 13 个大版本），用于新一批工作流场景。要求：

- 旧 v0.3.77 函数继续可用，存量用户的 dev 快照不受影响
- 新版本要支持现有的多租能力（user_id 隔离 input/output/cache/temp）
- 两版本可以并行 release、并行预热
- 用户实例启动时不会跨版本错加载快照（venv 不兼容）

### 1.3 关键约束

源码级调研（详见 §3）已验证：v0.3.77 → v0.16.4 之间，被 monkey-patch 的 4 个 ComfyUI 内部 API **签名与返回类型完全一致**，无需写适配器。这一结论决定了本设计的整体走向——把工作量全部放在「外围基础设施」（镜像构建 + 快照路径），**不动插件代码**。

## 2. 设计目标与非目标

### 2.1 目标

| # | 目标 | 验收 |
|---|---|---|
| G1 | 单条命令切换构建版本 | `make build-comfyui COMFYUI_VERSION=v0.16.4` 即可构建 |
| G2 | 默认行为零变化 | 不带参数的 `make build-comfyui` 仍构建 v0.3.77 镜像，标签格式不变 |
| G3 | 快照按版本隔离 | v0.3.77 实例不会加载到 v0.16.4 的快照（反之亦然） |
| G4 | OSS 基础快照按版本隔离 | 两版本的 `venv.tar.zst` 落在不同 OSS 前缀下 |
| G5 | 多租插件代码不动 | `FunArt-ComfyUI-Multi-User/` 的 7 个 .py 文件零改动 |
| G6 | 存量快照零迁移 | 已经在 `${MNT_DIR}/snapshots/` 下的 v0.3.77 快照仍能被 v0.3.77 实例读到 |

### 2.2 非目标

- **第三方插件在 v0.16.4 上的兼容性审计**：插件代码未改，但 v0.16.4 的 torch/transformers 等基础依赖会变，部分插件可能 pip 解析冲突或 import 失败。**这一步必须在 GPU 环境真实构建一次才能暴露**，非本提案能解决。
- **ComfyUI 官方 Asset 系统多租化**：v0.16.4 引入了 `app/assets/` 系统，自带 `owner_id` 概念，与本项目的 `X-FunArt-Comfy-UserId` 是平行体系。整合需要新的 patch 点，本提案不涉及。
- **v0.3.77 → v0.16.4 的用户工作流自动迁移**：节点 schema 在跨版本之间可能不兼容，用户的 workflow JSON 是否需要迁移不在本提案范围。
- **多租插件代码重构（adapter pattern 等）**：调研证明当前 patch 跨版本兼容，重构无收益。如果未来有第三个版本（v0.17+）出现 API 漂移，再考虑。

## 3. 关键调研结论

> 完整调研在调研期对两版完整源码做过 grep 与 diff。本节列出对设计有约束力的发现。

### 3.1 4 个 monkey-patch 点全部 API 兼容

| Patch 目标 | v0.3.77 签名 | v0.16.4 签名 | 兼容性 |
|---|---|---|---|
| `folder_paths.get_input_directory()` | `() -> str` (module fn) | **完全相同** | ✅ |
| `folder_paths.get_output_directory()` | `() -> str` | **完全相同** | ✅ |
| `folder_paths.get_temp_directory()` | `() -> str` | **完全相同** | ✅ |
| `folder_paths.get_user_directory()` | `() -> str` | **完全相同** | ✅ |
| `folder_paths.get_save_image_path(filename_prefix, output_dir, image_width=0, image_height=0)` | 4 参数 | **完全相同** | ✅ |
| `execution.PromptExecutor.execute(self, prompt, prompt_id, extra_data={}, execute_outputs=[])` | sync wrapper → `execute_async` | **完全相同**（v0.3.77 起就是此结构） | ✅ |
| `comfy_execution.caching.CacheKeySetInputSignature.get_immediate_node_signature(self, dynprompt, node_id, ancestor_order_mapping)` | async, returns list | **完全相同** | ✅ |
| `server.PromptServer.add_routes(self)` | aiohttp + `web.RouteTableDef()` | **完全相同**（仍是 aiohttp，未迁 FastAPI） | ✅ |

### 3.2 v0.16.4 新增的调用面不威胁 `DynamicPathProxy`

v0.16.4 新增 4 个文件调用 `folder_paths.get_*_directory()`（v0.3.77 无）：

| 文件 | 用法 | 是否戳穿 proxy |
|---|---|---|
| `app/assets/helpers.py` | `os.path.abspath(folder_paths.get_input_directory())` | ❌（`abspath` 走 `__fspath__`） |
| `app/assets/scanner.py` | `list_tree(folder_paths.get_input_directory())` → 内部 `os.path.abspath` | ❌ |
| `app/assets/api/routes.py:233` | `os.path.join(folder_paths.get_temp_directory(), "uploads")` | ❌（`os.path.join` 走 `__fspath__`） |
| `comfy_api_nodes/util/download_helpers.py:292` | `Path(get_output_directory())` | ❌（`pathlib.Path()` 走 `__fspath__`） |

全文搜索 v0.16.4 核心代码：**0 处** `isinstance(<path>, str)` / `json.dumps(<path>)` / `pickle.dumps(<path>)` / 路径用作 dict key 的模式。`DynamicPathProxy` 在 v0.16.4 上的有效作用窗口与 v0.3.77 完全等价。

### 3.3 v0.16.4 引入了官方 auth 字段（不影响本设计）

v0.16.4 新增 `extra_data['auth_token_comfy_org']` / `extra_data['api_key_comfy_org']`（`SENSITIVE_EXTRA_DATA_KEYS`），用于 ComfyUI 官方调用 comfy.org 云服务。**与本项目 user_id 隔离机制无冲突**——是平行的两套字段，但这给未来「让节点级代码也读到 user_id」留了一个可参考的官方机制。

### 3.4 `--user-directory` 与 v0.16.4 UserManager 的交互

当前 boot args 包含 `--user-directory ${MNT_DIR}/output`（`constants.py:84,104`）。v0.16.4 引入了 `UserManager`（`app/user_manager.py`），其行为：

- 当传入 `--multi-user` flag 时，`UserManager` 在 `--user-directory` 下按自有 user 体系创建子目录
- 当**未传** `--multi-user` 时（本项目情况），`UserManager` 退化为单用户模式，`--user-directory` 直接作为 user data 根，不创建子目录

**与本项目多租 patch 的关系**：

- `folder_paths_patch.py:140-145` 的 `_patched_get_user_directory` 已显式检查 `cli_args.args.multi_user`——若 ComfyUI 自带 multi-user 开启则不做二次隔离
- 本项目**不启用** ComfyUI 官方 `--multi-user`（受保护参数列表 `_PROTECTED_ARGS` 不含 `--multi-user`，但 `CUSTOM_BOOT_ARGS` 可传入；需在文档或代码层面禁止用户传入，避免双重隔离冲突）

**结论**：不冲突，但需在 `_PROTECTED_ARGS` 中**新增 `--multi-user`** 防止用户误开官方 multi-user 模式。

**待确认项（P3 阶段 GPU 实测）**：

- v0.16.4 的 `UserManager` 在单用户模式下是否会写 `users/default/` 子目录（如果是，与多租 patch 的 `users/<user_id>/` 目录会产生混淆）
- v0.16.4 的 `--user-directory` 是否还控制 workflow JSON 的存储位置（如果是，需确认多租 patch 的 `_patched_get_user_directory` 返回值是否正确覆盖）

### 3.5 DynamicPathProxy 的 `__hash__` / `__reduce__` 在 v0.16.4 上的安全性

`path_proxy.py` 主动禁止 hash 和 pickle——对 `DynamicPathProxy` 做 `hash()` 或放入 `set()`/`dict key` 会 raise `TypeError`。

**当前调研覆盖面**：§3.2 已确认 v0.16.4 核心代码"0 处 isinstance(path, str) / json.dumps / pickle.dumps / 路径用作 dict key"。但未覆盖以下模式：

| 潜在风险模式 | 触发后果 | 需搜索的 pattern |
|---|---|---|
| `set()` / `frozenset()` 含 path | `TypeError: unhashable` | `set(` + `folder_paths.get_*` 在同一个函数体内 |
| `@lru_cache` / `@cache` 参数含 path | `TypeError: unhashable` | 装饰器下的函数接收 path 参数 |
| `dict[path]` (path 做 key) | `TypeError: unhashable` | 赋值左侧 `[folder_paths.get_*()]` |
| `f-string` 或 `format()` 中 path | ✅ 安全 | `__format__` 已实现 |
| `Path(path)` | ✅ 安全 | `__fspath__` 已实现 |

**调研结论**：§3.2 的搜索已覆盖 "dict key" 模式，但对 `set()` 和 `@lru_cache` 模式的搜索**需要在 P3 GPU 首次构建时补做**。具体命令：

```bash
# 在 v0.16.4 源码目录下执行
grep -rn "lru_cache\|@cache" --include="*.py" | grep -v "test\|__pycache__"
grep -rn "set()\|frozenset(" --include="*.py" | xargs grep -l "folder_paths"
```

**缓解方案（如发现问题）**：将 `__hash__` 改为基于固定值（如 `id(self._path_getter)`）而非 raise；这会让 hash 稳定但不依赖 user_id，配合 `__eq__` 仍可正确比较。

### 3.6 多租 patch 的加载时序安全性

多租 patch 在 ComfyUI 加载 custom_nodes 时通过 `__init__.py` 安装（`import` 触发）。需确认 v0.16.4 是否改变了加载顺序。

**ComfyUI 启动时序**（v0.3.77 与 v0.16.4 一致）：

```
main.py
  → nodes.py: init_builtin_extra_nodes()     # 加载内置节点
  → nodes.py: init_external_custom_nodes()   # 扫描 custom_nodes/ 下的插件，import __init__.py
     └─ FunArt-ComfyUI-Multi-User/__init__.py  ← patch 在这里安装
  → server.PromptServer.add_routes()          # 注册 HTTP 路由
  → asyncio.run(run(...))                     # 启动事件循环，开始接受请求
```

**关键发现**：v0.16.4 的 `app/assets/` 模块是在 `server.py` 中 **lazy import** 的（`add_routes` 阶段才 import），而非启动时立即加载。这意味着：

- `app/assets/helpers.py` 调用 `folder_paths.get_input_directory()` 发生在 **patch 安装之后**
- 不存在 race condition

**但需验证的边界**：如果 v0.16.4 在 `nodes.py` 初始化过程中（加载内置节点时）调用了 `folder_paths.get_*_directory()`，且这发生在 `FunArt-ComfyUI-Multi-User` 被加载之前，则这些调用不会被 patch 拦截。**这不影响正确性**——初始化阶段不存在 user context，返回默认路径是正确行为。

**结论**：时序安全，无需适配。

## 4. 方案设计

### 4.1 代码组织

```
src/code/comfyui/
├── shared/                          ← 新增：版本无关的构建资源
│   ├── Dockerfile.template          ← 参数化 Dockerfile（替代当前 Dockerfile）
│   ├── Dockerfile.from_snapshot     ← 移自当前根目录
│   └── Makefile.common              ← 共享 build/upload/from-snapshot 目标
├── v0.3.77/                         ← 新增
│   ├── Makefile                     ← 仅 include common + 设定本版本变量
│   └── custom_nodes.json            ← 当前 custom_nodes_config/custom_nodes.json 移过来
├── v0.16.4/                         ← 新增
│   ├── Makefile
│   └── custom_nodes.json            ← 初版 = v0.3.77 复制；后续按兼容性结果裁剪
├── custom_nodes/                    ← 不动（FunArt-ComfyUI-Multi-User 等本地插件）
└── custom_nodes_config/             ← 保留 get_topn.py，custom_nodes.json 改为 symlink → v0.3.77/custom_nodes.json（向后兼容）
```

**代码迁移原则**：

- 物理移动：当前 `Dockerfile` → `shared/Dockerfile.template`（同时参数化）；当前 `custom_nodes_config/custom_nodes.json` → `v0.3.77/custom_nodes.json`
- 软链接兜底：`custom_nodes_config/custom_nodes.json` 留 symlink 指向 `v0.3.77/custom_nodes.json`，避免破坏可能存在的外部引用
- **不动**：`custom_nodes/`（本地自研插件，含多租插件）

### 4.2 镜像构建

#### 4.2.1 Dockerfile 参数化

`shared/Dockerfile.template` 在当前 `Dockerfile` 基础上做四点修改：

1. 顶部增加 ARG：
   ```dockerfile
   ARG COMFYUI_VERSION                    # 必填，e.g. v0.3.77 / v0.16.4
   ARG CUSTOM_NODES_JSON                  # 必填，相对 build context 的路径
   ```
2. 替换 `git checkout "v0.3.77"` 为 `git checkout "${COMFYUI_VERSION}"`
3. 替换 `COPY code/comfyui/custom_nodes_config/custom_nodes.json /tmp/custom_nodes.json` 为 `COPY ${CUSTOM_NODES_JSON} /tmp/custom_nodes.json`
4. 在 `codes` stage 末尾写入版本标识文件：
   ```dockerfile
   RUN echo "${COMFYUI_VERSION}" > ${COMFYUI_DIR}/.funart-comfyui-version
   ```
   该文件供运行时探测（见 §4.3.1）

**保持不变**：当前 Dockerfile 中所有 pip install / 强制重装依赖 / nunchaku / vision-plaid / sam2 / insightface 的逻辑——这些是 v0.3.77 当前生产链路的一部分，新版本先保持一致再按需调整（属于「非目标」中第三方插件兼容性问题的范畴）。

#### 4.2.2 子目录 Makefile

`v0.3.77/Makefile`：

```makefile
COMFYUI_VERSION := v0.3.77
CUSTOM_NODES_JSON := src/code/comfyui/v0.3.77/custom_nodes.json

# OSS 路径自动按版本前缀
OSS_COMFYUI_BASE_DIR := base/comfyui/$(COMFYUI_VERSION)-gamma
OSS_COMFYUI_DEEPGPU_BASE_DIR := base/comfyui/$(COMFYUI_VERSION)-gamma-deepgpu

include ../shared/Makefile.common
```

`v0.16.4/Makefile` 仅 `COMFYUI_VERSION` 不同。

`shared/Makefile.common` 收纳当前 `src/code/comfyui/Makefile` 中的 `build` / `run` / `exec` / `upload-base` / `upload-deepgpu-base` / `build-from-snapshot` / `update-custom-nodes` 目标，把 `git checkout` 行为参数化、把 OSS 路径变量化。

#### 4.2.3 顶层 Makefile

新增/修改：

```makefile
COMFYUI_VERSION ?= v0.3.77    # 默认值保证 G2

build-comfyui: build
	@$(MAKE) -C src/code/comfyui/$(COMFYUI_VERSION) build

build-comfyui-v0.3.77:
	@$(MAKE) build-comfyui COMFYUI_VERSION=v0.3.77

build-comfyui-v0.16.4:
	@$(MAKE) build-comfyui COMFYUI_VERSION=v0.16.4

build-comfyui-all: build-comfyui-v0.3.77 build-comfyui-v0.16.4
```

`run-comfyui` / `exec-comfyui` / `upload-comfyui-base` 同样按 `COMFYUI_VERSION` 路由到对应子目录。

#### 4.2.4 镜像 tag 规范

| 当前 | 新规范 |
|---|---|
| `comfyui:v1.6.5` | `comfyui:<plugin-set-ver>-comfyui-<comfyui-ver>`，例 `comfyui:v1.6.5-comfyui-v0.3.77` |

**兼容性**：v0.3.77 镜像继续也额外打 `comfyui:v1.6.5` tag（旧 tag），避免外部引用断裂。

### 4.3 Agent 运行时

#### 4.3.1 版本感知

`src/code/agent/constants.py` 新增：

```python
def _read_comfyui_version() -> str:
    """从镜像构建期写入的标识文件读 ComfyUI 版本。读不到时返回 ''（保持旧行为）。"""
    path = os.path.join(COMFYUI_DIR, ".funart-comfyui-version")
    try:
        with open(path) as f:
            return f.read().strip()
    except Exception:
        return ''

COMFYUI_VERSION = os.getenv('COMFYUI_VERSION') or _read_comfyui_version()
```

**优先级**：环境变量（外部覆盖能力） > 构建期写入的版本文件 > 空字符串（兜底）。

#### 4.3.2 快照路径按版本隔离

`SNAPSHOT_DIR` 从「常量」改为「按版本计算」：

```python
# 旧
SNAPSHOT_DIR = MNT_DIR + '/snapshots'

# 新
if COMFYUI_VERSION:
    SNAPSHOT_DIR = f"{MNT_DIR}/snapshots/{COMFYUI_VERSION}"
else:
    SNAPSHOT_DIR = f"{MNT_DIR}/snapshots"   # 旧实例（无版本文件）退化到旧路径
```

**存量兼容**（满足 G6）：旧的 v0.3.77 镜像没写 `.funart-comfyui-version`，`COMFYUI_VERSION=''`，`SNAPSHOT_DIR` 走兜底分支等于旧路径，原有 `${MNT_DIR}/snapshots/dev-*` 仍可被加载。新构建的 v0.3.77 镜像写了版本，会去新路径 `${MNT_DIR}/snapshots/v0.3.77/` 找——需要一次性迁移（详见 §6.1）。

**Fallback 优先级规则**：

1. **新路径优先**：`find_valid_snapshots` 先扫 `SNAPSHOT_DIR`（含版本前缀的新路径），仅当新路径为空时才扫旧路径 `${MNT_DIR}/snapshots/`
2. **不做 dedup**：两个目录不会有同名快照（新路径还未写过时旧路径有数据；一旦新路径有了，后续只写新路径），合并后按时间戳排序即可
3. **`_is_snapshot_loadable` 适配**：该方法内部拼路径 `os.path.join(constants.SNAPSHOT_DIR, snapshot_name)`，当快照来自旧路径时需传完整路径或在调用处适配。推荐在 `find_valid_snapshots` 返回值中附带目录前缀信息（返回 `(dir, name)` tuple 而非纯 name），或在内部统一转为绝对路径

**`snapshot_saver` 清理逻辑适配**：

`snapshot_saver.py:62-106` 的 `_cleanup_old_snapshots` 只 `os.listdir(constants.SNAPSHOT_DIR)`。改造后：

- **旧路径的快照不纳入清理**（防止误删存量用户数据）
- 清理逻辑只管新路径 `${MNT_DIR}/snapshots/<version>/` 下的快照
- 旧路径快照由"自然演进"策略处理：用户下次 save 时写到新路径，旧快照不再被读取后自然过期
- 如果旧路径磁盘空间成为问题，可在 v0.3.77 退场后统一清理（§9.3 待决问题）

被影响的代码路径：

- `services/workspace/snapshot_manager.py:51, 136, 201, 224` 全部读 `constants.SNAPSHOT_DIR`，自动跟随
- `services/workspace/snapshot_loader.py` / `snapshot_saver.py` 中的路径同理
- `routes/routes.py` `/pre-stop` 中 `mgr.cleanup_incomplete_save(snapshot_name)` 自动跟随

#### 4.3.3 OSS 基础快照按版本隔离

`api` 模式启动时从 OSS 拉的基础 venv/comfyui 包，对应 OSS 前缀 `base/comfyui/<version>-gamma/`。当前由 `OSS_COMFYUI_BASE_DIR` env 传入（具体加载逻辑在 `snapshot_loader.py` 的 `ComfyUIProdSnapshotLoader`）。

**改动**：保留 env 注入方式不变，但在 `s.yaml` 模板中把 `OSS_COMFYUI_BASE_DIR` 默认值与 `COMFYUI_VERSION` 联动：

```yaml
environmentVariables:
  COMFYUI_VERSION: ${vars.comfyuiVersion}
  OSS_COMFYUI_BASE_DIR: 'base/comfyui/${vars.comfyuiVersion}-gamma'
```

### 4.4 entrypoint.bash

`entrypoint.bash` 当前没读版本，改动不大——只在启动 banner 中打印一行版本信息便于排查：

```bash
COMFYUI_VERSION=$(cat ${COMFYUI_DIR}/.funart-comfyui-version 2>/dev/null || echo "unknown")
echo "[INFO] ComfyUI version: ${COMFYUI_VERSION}"
```

#### 4.4.1 ComfyUI Manager 配置兼容性

`entrypoint.bash:70-139` 的 `setup_comfyui_manager_config` 检查两个路径：
- `${MNT_DIR}/output/__manager`（新版 ComfyUI Manager）
- `${MNT_DIR}/output/default/ComfyUI-Manager`（旧版）

**v0.16.4 兼容性评估**：

- v0.16.4 搭配的 ComfyUI Manager 版本可能变化了 config 目录结构（如从 `config.ini` 迁移到 JSON 格式）
- 当前 overlay 逻辑拷贝 `channels.list` 和 `config.ini`——如果新版 Manager 不再读这两个文件，overlay 变为无效操作（不报错但不生效）

**处理方案**：

- P3 首次构建时检查 v0.16.4 镜像内 ComfyUI Manager 的实际 config 路径和格式
- 如果格式变了，在 `services/proxy/comfyui_manager_config/` 下按版本放两套配置
- `setup_comfyui_manager_config` 按 `COMFYUI_VERSION` 环境变量选择对应配置目录：

```bash
# 按版本选配置源
if [[ "${COMFYUI_VERSION_DETECTED}" == v0.16.* ]]; then
  CONFIG_SRC="${AGENT_DIR}/services/proxy/comfyui_manager_config/v0.16"
else
  CONFIG_SRC="${AGENT_DIR}/services/proxy/comfyui_manager_config"
fi
```

## 5. 方案对比

### 5.1 备选 A：单镜像 + 运行时切换

**机制**：一张镜像同时 ship 两个版本的 ComfyUI 源码与 venv，启动时按 env 选一个。

**否决理由**：
- 镜像膨胀至少 3-4GB（venv 不能共用）
- 冷启动拉镜像更慢、占 NAS 缓存更多
- 没有解决依赖冲突——两版的 torch 不能共存于同一个 venv

### 5.2 备选 B：插件代码写 adapter pattern

**机制**：`comfyui-multi-user/` 拆 `core/` + `adapters/v0_3/` + `adapters/v0_16/`，启动时探测版本选择 adapter。

**否决理由**：
- §3.1 已证明两版本 4 个 patch 点 API 完全一致，adapter 内 90% 代码会重复
- 增加抽象层带来的认知成本和测试矩阵成本，无对应收益
- 真有第三个版本出现 API 漂移时再做也不迟（YAGNI）

### 5.3 备选 C：运行时探测 ComfyUI 版本（不写版本文件）

**机制**：通过 import `comfy.cli_args` 或读 `comfyui/.git/HEAD` 来判断。

**否决理由**：
- 启发式探测不稳定（git 元数据可能在生产构建时被 strip；`__version__` 不一定在所有版本都有）
- 调试性差——出问题时无法直接 `cat` 一个文件确认
- 构建期写文件成本极低（一行 RUN echo），收益更高

**采用的方案**：env var > 构建期写入文件 > 空字符串兜底。

## 6. 影响面

### 6.1 存量快照的迁移

**问题**：新构建的 v0.3.77 镜像（写入版本文件后）会去 `${MNT_DIR}/snapshots/v0.3.77/` 找快照，但用户存量快照都在 `${MNT_DIR}/snapshots/` 下。

**方案 A（自动）**：`SnapshotManager.load()` 在新路径找不到时，回退到旧路径并打 deprecation 日志。1~2 个版本后移除回退。

**方案 B（迁移脚本）**：发布一次性脚本，遍历所有用户 NAS 把 `snapshots/dev-*` 移到 `snapshots/v0.3.77/dev-*`。

**推荐 A**——零运维负担，用户无感。Read-only fallback，写入只写新路径，自然演进到新结构。

### 6.2 现有 CI / 发布流程

| 命令 | 现有行为 | 新行为 |
|---|---|---|
| `make build` | 构建 agent 镜像 | **不变** |
| `make build-comfyui` | 构建 v0.3.77 comfyui 镜像 | **不变**（默认 `COMFYUI_VERSION=v0.3.77`） |
| `make all` | 预发流程 | **不变** |
| `make release VERSION=v1.4.0` | prod release v0.3.77 | **不变** |
| `make build-comfyui COMFYUI_VERSION=v0.16.4` | n/a | 新增能力 |
| `make release VERSION=v1.4.0 COMFYUI_VERSION=v0.16.4` | n/a | 新增能力 |

### 6.3 OSS 上传

| 路径 | 现有 | 新 |
|---|---|---|
| `oss://dipper-cache-{region}/base/comfyui/v0.3.77-gamma/` | 已在用 | 仍在用，由 v0.3.77/Makefile 上传 |
| `oss://dipper-cache-{region}/base/comfyui/v0.16.4-gamma/` | 不存在 | 新增，由 v0.16.4/Makefile 上传 |

需要发起人手动跑一次 `make -C src/code/comfyui/v0.16.4 upload-base` 完成首轮上传。

### 6.4 用户函数配置

存量函数继续用旧镜像 + 旧 OSS 前缀，不受影响。

新建 v0.16.4 函数时需在 s.yaml 设置 `COMFYUI_VERSION: v0.16.4` 与对应 OSS 前缀。建议在 build-your-own/ 模板中加一份 v0.16.4 示例。

### 6.5 Python 版本兼容性

当前 Dockerfile 使用 **`python:3.10.16-slim`** 作为基础镜像（`Dockerfile:85,152,172`），对应 CPython 3.10。

**影响评估**：

| 依赖 | 当前状态 | v0.16.4 要求 | 风险 |
|---|---|---|---|
| ComfyUI v0.16.4 core | 未确认 | 需查 `pyproject.toml` 的 `requires-python` | 中（v0.16.4 可能要求 ≥3.11） |
| nunchaku wheel | `cp310-cp310-linux_x86_64.whl` | 仅提供 cp310 | 高（若升 Python 则无 wheel） |
| torch 2.9.1 | cp310 支持 | cp310/cp311/cp312 都有 | 低 |
| vision-plaid / sam2 | pip install from source | 一般支持 3.10+ | 低 |

**决策树**：

1. P3 阶段 `git clone ComfyUI && git checkout v0.16.4 && cat pyproject.toml` 确认 `requires-python`
2. 如果 v0.16.4 **兼容 Python 3.10**：无需改 Dockerfile 基础镜像，最低成本
3. 如果 v0.16.4 **要求 ≥3.11**：
   - Dockerfile 改为 `python:3.11-slim`
   - nunchaku wheel 需要 upstream 提供 cp311 版本（或从源码编译）
   - 这会是 P3→P4 阶段最大的工作量来源

**建议**：先按 Python 3.10 构建，如果失败再升。不要预先升级——Python 版本变更影响面极大（所有 C extension wheel 都要重新匹配）。

## 9. 开放问题

### 9.1 ComfyUI 官方 Asset 系统是否需要多租化

v0.16.4 的 `app/assets/api/routes.py` 提供了 `/api/assets` 系列 HTTP 端点，按 ComfyUI 自有的 `UserManager.get_request_user_id(request)` 隔离。这套**与本项目的 user_id 是平行的两条线**，意味着：

- 用户 A 调用 `/api/assets` 列资产时，看到的是 ComfyUI 默认 user 的资产（不分租）
- 多租隔离的 input/output 文件**不会**自动被识别为「用户 A 的资产」

**待决**：
- 短期：在 v0.16.4 镜像的启动参数里关掉 Asset 系统（如有 disable flag）
- 中期：写第 5 个 patch（patch `UserManager.get_request_user_id`），把 ComfyUI 的 user 体系桥接到 `X-FunArt-Comfy-UserId`

### 9.2 `custom_nodes.json` 双版本如何长期维护

短期内 v0.3.77 与 v0.16.4 的清单大概率会出现 drift（v0.16.4 上某些插件需要更新版本）。

**待决**：
- 是否在 `update-custom-nodes` 脚本里支持版本参数（`make update-custom-nodes n=200 COMFYUI_VERSION=v0.16.4`）
- 是否需要一个 diff 工具自动检测两版差异

### 9.3 v0.3.77 的退场时间表

引入 v0.16.4 后，v0.3.77 还要维护多久？这影响到 §6.1 fallback 逻辑何时移除、§4.2.4 旧 tag 何时停发。

**待决**：与产品 / 运维对齐 v0.3.77 的 EOL 计划。

## 附录 C：版本号体系与镜像分发链路澄清

> 仓库里同时存在三个互不相关的「版本号」和两套镜像 registry，新人 review 本提案时极易混淆。本附录梳理三者关系，作为本提案 §4.2.4 镜像 tag 规范的前置背景。

### C.1 三个版本号（互不相关）

| 版本号 | 例值 | 定义位置 | 含义 | 谁会读它 |
|---|---|---|---|---|
| **ComfyUI 官方版本** | `v0.3.77` / `v0.16.4` | `src/code/comfyui/Dockerfile:12`<br>`git checkout "v0.3.77"` | ComfyUI 上游代码版本 | docker build 时 git checkout |
| **FunArt 镜像配置版本** | `v1.6.5` | `src/code/comfyui/Makefile:3`<br>`COMFYUI_IMAGE = comfyui:v1.6.5` | FunArt 自定的"内置插件集合 + 构建配置"版本号；每升级 torch / 加新插件就 bump | `dependency_version.txt`<br>`builtin_custom_nodes.py` 兼容性检查 |
| **Agent 镜像 git 版本** | `v1.4.0` | `make release VERSION=v1.4.0`<br>顶层 `Makefile:36` | 整个 agent 镜像在 ACR 的 tag；通常等于 git tag | s.yaml `customContainerConfig.image` |

**重点 1**：`comfyui:v1.6.5` **不是用户启动函数用的镜像**，它只是 `make build-comfyui` 后留在本地 docker 上的临时 tag，**不会被 push 到任何 registry**。仓库里所有 `s.yaml` 模板的 `image:` 字段都不引用它。

**重点 2**：版本号没有 implicit 关联。`v1.6.5` 跟 `v0.3.77` 没有"包含"关系，也不会因 ComfyUI 升级到 v0.16.4 自动变化。这就是为什么本提案 §4.2.4 提议把镜像 tag 改成 `comfyui:v1.6.5-comfyui-v0.3.77` 这种**双段式**——把两个独立维度都显式写出来。

### C.4 镜像分发链路（含 warmup 机制）

```
┌──────────────────────────────────────────────────────────────────────┐
│  阶段 1：构建 + push                                                  │
│  ─────────────────────────────────────                               │
│  make release VERSION=v1.4.0                                         │
│  └─→ docker build → docker push                                       │
│       cap-demo-public-registry.cn-hangzhou.cr.aliyuncs.com/cap-app/  │
│         image-generation-comfyui-agent:v1.4.0                        │
└──────────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│  阶段 2：多 region 预热（warmup/warmup.sh）                           │
│  ─────────────────────────────────────                               │
│  for region in cn-hangzhou cn-shenzhen cn-beijing                    │
│                cn-shanghai ap-southeast-1; do                        │
│      s deploy -t s-warmup.yaml    （image=v1.4.0）                    │
│  done                                                                │
│                                                                      │
│  作用：在每个 region 部署一个 dummy "FuncAI-warmup-agent-{ver}"      │
│        函数 → 触发 FC 平台到该 region 的 worker 节点池预拉镜像        │
│        预热完毕后，每个 region 的 worker 都缓存了这份镜像              │
└──────────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│  阶段 3：业务方 / 用户部署函数                                        │
│  ─────────────────────────────────────                               │
│  s deploy -t s-api-usemodel.yaml                                     │
│  └─→ FC 创建函数，customContainerConfig.image = v1.4.0               │
│      （FC 把这个 image 字段记到函数配置里，未实际拉取）                │
└──────────────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────────┐
│  阶段 4：用户首次调用 → FC 实例冷启动                                 │
│  ─────────────────────────────────────                               │
│  FC 调度 worker → worker 已有镜像缓存（阶段 2 预热的成果）             │
│  → 直接启动容器，无跨网络拉取                                         │
│                                                                      │
│  ⚠ 若某 region 跳过了预热（或预热失败）：                             │
│    worker 首次启动需从 ACR 拉镜像（GB 级，可能数十秒）                │
│    冷启动时延会显著增加                                               │
└──────────────────────────────────────────────────────────────────────┘
```

**预热的本质**：阿里云 FC 的镜像缓存是 **region 级 worker 节点池**。warmup 步骤通过"在该 region 主动部署一次"强制 FC 把镜像分发下去，避免真实用户首次调用时承担镜像拉取延迟。
