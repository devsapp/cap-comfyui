# 多版本 ComfyUI 测试、升级与回退方案

**日期**：2026-05-19
**状态**：草稿（与 `design-2026-05-18.md` 配套使用）
**关联设计**：`./design-2026-05-18.md`

## 摘要（TL;DR）

本文档是 v0.16.4 多版本设计的配套实施文档，回答三个落地必答题：

1. **怎么测**——分 5 层测试，明确各层范围与稳定性挑战的对策
2. **怎么平滑升级**——存量函数零打扰、终端用户无感、分阶段灰度
3. **怎么回退**——以路径隔离为基础，镜像 tag 回滚秒级生效；明确不可逆动作的红线

核心原则：**回退不应该删除任何数据**。多版本路径隔离让"换镜像即回退"成为可能。

## 1. 测试方案

### 1.1 测试分层

| 层级 | 范围 | 跑在哪 | CI 触发 |
|---|---|---|---|
| **L1 单测** | `constants.py` 路径计算、`SnapshotManager` fallback、`parse_auto_install_nodes` 等纯逻辑 | 任意机器（无 GPU） | 每次 PR |
| **L2 容器集成测试** | 镜像内启动 agent + ComfyUI（CPU 模式），跑 `/management/start`、`/initialize`、`/pre-stop` | docker container（CPU） | 每次 PR |
| **L3 GPU 烟囱测试** | 真 GPU 实例，跑预制 workflow，对比输出 hash | GPU 节点（fc.gpu.tesla.1） | merge 后 + nightly |
| **L4 多租隔离回归** | 双用户并发，验证 input/output/cache 路径分离 | GPU 节点 | merge 后 |
| **L5 灰度生产监控** | cn-hangzhou 单 region，观察真实流量指标 | 生产 region | release 后 |

**重点：L3 必须做。** 设计文档 §7 风险表里"v0.16.4 第三方插件 import 失败"概率高。GPU 上不实跑一次，纸面调研发现不了 nunchaku/transformers/torch 的实际兼容性问题。

### 1.2 测试稳定性的常见根因与对策

ComfyUI 类系统的测试不稳定根因复杂——既有 ML 推理本身的非确定性，也有 ComfyUI 的工作流执行模型，还有跨 NAS/OSS 的 IO 抖动。需要逐项消除。

| 不稳定来源 | 现象 | 对策 |
|---|---|---|
| **ComfyUI 启动时间抖动** | `wait_until_ready` 偶尔超过 `READINESS_TIMEOUT` | 测试用 `READINESS_TIMEOUT=1800`（生产 900），给冷启动留余量 |
| **GPU 节点池调度抖动** | 实例冷启动慢导致 e2e 超时 | 单独的 dedicated 测试函数，提前 warmup；或用预留实例 |
| **第三方插件 pip 解析非确定** | 同 requirements.txt 不同时间 install 拉到不同版本 | 锁定 pip 索引快照（`--index-url=https://py-index.oss.../snapshot-2026-05-18/`）；或测试镜像复用构建产物，不重新 install |
| **ComfyUI workflow 输出非确定** | 同 prompt 不同 seed 出图不同 | 测试 prompt 显式 fix `seed`、关掉 sampler 随机性；对比方式从"像素逐位"改为 perceptual hash 或 latent 距离 |
| **NAS / OSS 网络抖动** | 快照 download 偶尔失败 | retry 3 次 + 缓存到本地；测试对网络错误**显式断言**而非超时 |
| **快照间相互污染** | 多个测试共用同一 NAS 路径 | 每次测试用独立 `${MNT_DIR}=/mnt/test/{ts}-{run-id}/`；测后清理（CI hook） |
| **多租 patch 副作用** | 测试 A 影响测试 B（monkey-patch 全局） | 每个 multi-tenant 测试启独立 ComfyUI 子进程；不要复用 |
| **flaky 偶发** | 不可复现的失败 | CI 配 `--reruns=2`；记录日志到 OSS 留存；任何 flaky 必须 root cause，**不留 quarantine** |

### 1.4 L3 GPU 输出对比方案

#### 1.4.1 工具与阈值

使用 `imagehash` 库的 **dhash**（差异哈希），阈值 ≤ 8 位（256 bit 中最多 8 bit 不同）判定"跨版本输出一致"。

```python
import imagehash
from PIL import Image

def assert_perceptual_match(img_path_a: str, img_path_b: str, threshold: int = 8):
    """断言两张图片的感知哈希距离在阈值内"""
    hash_a = imagehash.dhash(Image.open(img_path_a), hash_size=16)
    hash_b = imagehash.dhash(Image.open(img_path_b), hash_size=16)
    distance = hash_a - hash_b
    assert distance <= threshold, (
        f"Perceptual diff too large: {distance} > {threshold}\n"
        f"  Image A: {img_path_a}\n"
        f"  Image B: {img_path_b}"
    )
```

#### 1.4.2 测试 Prompt 集合

放在 `src/code/agent/test/fixtures/benchmark_prompts/`：

| 文件 | 内容 | 目的 |
|---|---|---|
| `txt2img_fixed_seed.json` | 固定 seed=42、sampler=ddim、steps=20、512x512 | 最基础出图 |
| `img2img_controlnet.json` | ControlNet canny + 固定 seed | 验证条件生成 |
| `workflow_multi_node.json` | 多节点拼接（upscale + face restore） | 验证复杂工作流 |

所有 prompt 必须：`"seed": 42`、`"control_after_generate": "fixed"`、无随机 sampler。

#### 1.4.3 构建幂等性校验

Docker 构建不保证 image sha256 一致（metadata timestamp 变化），用以下替代方案验证 G2：

```bash
# 对比关键路径的文件列表 + size（排除版本标识文件）
compare_image_fs() {
  local img=$1
  docker run --rm "$img" find /root/comfyui /root/venv/lib \
    -not -name '.funart-comfyui-version' \
    -printf '%p %s\n' | sort | sha256sum
}

HASH_BEFORE=$(compare_image_fs comfyui:v1.6.5-before-refactor)
HASH_AFTER=$(compare_image_fs comfyui:v1.6.5-comfyui-v0.3.77)
[ "$HASH_BEFORE" = "$HASH_AFTER" ] || echo "FAIL: filesystem content differs"
```

更轻量级的检查（CI 最低要求）：对比 `pip freeze` 输出 + ComfyUI git hash + custom_nodes 列表。

### 1.5 针对本提案的测试用例清单

按设计文档 §2.1 的 G1-G6 各打一个或多个用例：

| 验收点 | 测试 | 形式 |
|---|---|---|
| **G1 单条命令切换** | `make build-comfyui COMFYUI_VERSION=v0.16.4` 产物可启动 | L2 |
| **G2 默认零变化** | `make build-comfyui` 无参数构建，与改造前 sha256 一致（除版本文件） | CI script + L1 |
| **G3 快照按版本隔离** | 双版本实例并存，验证 NAS 路径前缀隔离、不串扰 | L3 |
| **G4 OSS 隔离** | `oss ls dipper-cache.../base/comfyui/` 看到两个版本目录都健康 | L3 |
| **G5 多租插件代码不动** | `git diff main..HEAD -- src/code/comfyui/custom_nodes/FunArt-ComfyUI-Multi-User/` 必须为空（CI 强校验） | CI script |
| **G6 存量快照零迁移** | 旧 NAS（无版本前缀目录）+ 新 agent 镜像，能成功加载 | L3 + L5 |

**特别要点**：G2 的"sha256 一致"是行为零变化的硬性检查。CI 上加一个 step，对比改造前后镜像内除 `.funart-comfyui-version` 外所有 layer 的内容 hash。这是防止重构悄悄改了行为最有效的护栏。

### 1.6 双用户多租隔离的"金标准"测试

```python
# L4 测试模板
def test_multi_user_isolation_v0_16_4():
    # 启动 v0.16.4 实例
    instance = launch_function(version='v0.16.4')

    # 用户 A 提交一个出图 workflow
    resp_a = instance.post('/api/serverless/run',
                           headers={'X-FunArt-Comfy-UserId': 'user-a'},
                           json={'prompt': WORKFLOW_FIXED_SEED})

    # 用户 B 提交相同 workflow
    resp_b = instance.post('/api/serverless/run',
                           headers={'X-FunArt-Comfy-UserId': 'user-b'},
                           json={'prompt': WORKFLOW_FIXED_SEED})

    # 断言 1：output 路径分离
    assert resp_a['output_path'].startswith('users/user-a/')
    assert resp_b['output_path'].startswith('users/user-b/')

    # 断言 2：缓存命中分离（B 应该重新执行而非命中 A 的 cache）
    assert resp_b['execution_time'] >= resp_a['execution_time'] * 0.5

    # 断言 3：NAS 实际目录隔离
    assert os.path.exists(f'/mnt/auto/output/users/user-a/{resp_a["filename"]}')
    assert os.path.exists(f'/mnt/auto/output/users/user-b/{resp_b["filename"]}')
    # 反向断言 A 看不到 B 的文件
    assert not os.path.exists(f'/mnt/auto/output/users/user-a/{resp_b["filename"]}')
```

**用法**：跑两次，一次 v0.3.77 一次 v0.16.4，确保多租 patch 在两个版本上行为一致（这是 G3 + G5 的联合验收）。

### 1.8 并发多租隔离测试

§1.6 是顺序执行的，生产环境是多用户并发。需要验证并发下 `contextvars` 隔离不串扰。

```python
import asyncio
import aiohttp

async def test_concurrent_multi_user_isolation():
    """两个用户同时提交 workflow，验证并发下路径隔离不串扰"""
    base_url = 'http://localhost:9000'

    async def submit_workflow(session, user_id):
        headers = {'X-FunArt-Comfy-UserId': user_id}
        async with session.post(
            f'{base_url}/api/serverless/run',
            headers=headers,
            json={'prompt': WORKFLOW_FIXED_SEED}
        ) as resp:
            return await resp.json()

    async with aiohttp.ClientSession() as session:
        # 并发提交 —— 模拟两个用户同时到达
        results = await asyncio.gather(
            submit_workflow(session, 'user-concurrent-a'),
            submit_workflow(session, 'user-concurrent-b'),
        )

    resp_a, resp_b = results

    # 断言 1：路径隔离
    assert 'user-concurrent-a' in resp_a['output_path']
    assert 'user-concurrent-b' in resp_b['output_path']

    # 断言 2：不串扰（A 的输出不出现在 B 的目录）
    assert resp_a['output_path'] != resp_b['output_path']
    assert 'user-concurrent-b' not in resp_a['output_path']
    assert 'user-concurrent-a' not in resp_b['output_path']


async def test_concurrent_execution_with_prestop():
    """一个用户执行 workflow 的同时另一个实例触发 pre-stop，验证不冲突"""
    base_url = 'http://localhost:9000'

    async with aiohttp.ClientSession() as session:
        # 并发：workflow 执行 + pre-stop
        workflow_task = asyncio.create_task(
            session.post(f'{base_url}/api/serverless/run',
                        headers={'X-FunArt-Comfy-UserId': 'user-x'},
                        json={'prompt': WORKFLOW_FIXED_SEED})
        )
        # 延迟 100ms 后触发 pre-stop（模拟实例缩容）
        await asyncio.sleep(0.1)
        prestop_task = asyncio.create_task(
            session.post(f'{base_url}/pre-stop')
        )

        workflow_resp, prestop_resp = await asyncio.gather(
            workflow_task, prestop_task, return_exceptions=True
        )

    # workflow 要么成功完成，要么返回明确的错误（不能 500/crash）
    if not isinstance(workflow_resp, Exception):
        async with workflow_resp:
            assert workflow_resp.status in (200, 409, 503)  # 200=成功, 409/503=实例正在关停
```

## 2. 存量平滑升级

### 2.1 先把"存量"分清楚

| 存量对象 | 是否需要主动升级 | 兼容方式 |
|---|---|---|
| **已部署的 v0.3.77 FC 函数实例** | ❌ 不需要 | 镜像 tag 不变，继续跑 |
| **NAS 上的用户 dev 快照** | ❌ 不需要 | 设计文档 §6.1 fallback：新代码自动读旧路径 |
| **OSS `base/comfyui/v0.3.77-gamma/` 基础包** | ❌ 不需要 | 路径保留，新增 `v0.16.4-gamma/` 不影响旧路径 |
| **用户 workflow JSON** | ⚠️ 可能需要 | ComfyUI 跨大版本 schema 可能变；设计文档 §2.2 列为非目标 |

**结论**：本提案的"存量平滑"主要靠两个机制：

1. **默认行为不变**（设计文档 §2.1 G2）：用户不主动改 s.yaml，继续部署得到 v0.3.77 镜像
2. **代码路径双向兼容**（设计文档 §4.3.2 + §6.1 方案 A）：新 agent 同时支持新旧 NAS 路径

### 2.2 升级路径（按角色）

**对存量函数所有者（business 团队 / 部署方）**：

```
当前状态：image: cap-demo-public-registry.../comfyui-agent:v1.4.0  (隐含 v0.3.77)
   ↓ 第 1 步：升 agent 不升 ComfyUI（验证新代码本身稳定）
image: cap-demo-public-registry.../comfyui-agent:v1.5.0-comfyui-v0.3.77
   ↓ 第 2 步：单函数试切到 v0.16.4
image: cap-demo-public-registry.../comfyui-agent:v1.5.0-comfyui-v0.16.4
环境变量增加: COMFYUI_VERSION=v0.16.4
              OSS_COMFYUI_BASE_DIR=base/comfyui/v0.16.4-gamma
   ↓ 第 3 步：观察 1-2 周
   ↓ 第 4 步：批量切换其它函数
```

**对终端用户（end user）**：完全无感。请求路径不变（`/api/serverless/*`、`/api/*`、`/ws`），多租 user_id 隔离不变。唯一可能的影响是某些工作流在 v0.16.4 上节点 schema 不兼容（这是设计文档 §2.2 的非目标）。

### 2.3 灰度策略

| 阶段 | 范围 | 持续时间 | 停止条件 |
|---|---|---|---|
| **G0 内部 dev 函数** | quanxi-zijian 账号一个测试函数 | 2-3 天 | 跑完 §1 全部 e2e |
| **G1 单 region 灰度** | cn-hangzhou，1-2 个生产函数 | 1 周 | 错误率 / 延迟 / 出图质量与 v0.3.77 持平 |
| **G2 多 region 灰度** | 增加 cn-shanghai、cn-shenzhen | 3-5 天 | 同上 |
| **G3 全量** | 全 5 个 region 都可选 v0.16.4 | — | 用户自主选择 |

**关键监控指标**（每个灰度阶段都要看，详见 §4）：

- 函数冷启动时延 P50 / P99
- `/initialize` 成功率
- 工作流执行成功率（按 user_id 维度切片）
- ComfyUI 子进程 OOM / 崩溃次数（liveness 触发的重启次数）
- pip install 失败的插件名（构建期 + 运行期）
- 出图 perceptual diff（vs 同 prompt 在 v0.3.77 的产出）

监控看板建议在落地阶段（设计文档 §8 P5 之前）就准备好，否则灰度时只能看日志。

### 2.4 双轨期持续多久

设计文档 §9.3 列为待决问题。本文档建议：

- **最少 1 个 release cycle**（约 1-2 个月）：让所有积极用户都迁移
- **最多到下一次大版本（v0.17+）出现前**：避免维护 3 套
- **退出节点**：v0.3.77 镜像停止 push 新 tag、停止 warmup → 现存函数仍可跑（FC 已缓存的镜像不会主动清）→ 用户可控自己的迁移节奏

## 3. 回退方案

### 3.1 失败模式分类

回退策略要区分**什么环节出问题**，不同环节回退动作完全不同：

| 失败模式 | 何时发现 | 回退动作 | 时延 |
|---|---|---|---|
| **A. 镜像构建失败** | CI / make build | 不发布，不进入回退流程 | n/a |
| **B. 镜像构建过但启动崩溃** | 灰度 G0/G1 | 修镜像，重新发版 | 几小时 |
| **C. ComfyUI 进程能起，但工作流失败** | 灰度 G0/G1 | 改 s.yaml `image` 回退到旧 tag → s deploy | 5 分钟 |
| **D. 灰度阶段出图质量退化** | G1/G2 监控告警 | 同 C | 5 分钟 |
| **E. 全量发布后才发现某 region 问题** | G3 后 | 单 region s deploy 回退 | 5 分钟 |
| **F. 用户已在 v0.16.4 保存了 dev 快照，需回退到 v0.3.77** | 用户报告 | ⚠️ 见 §3.3 | — |

### 3.2 镜像层回退（C/D/E）

**前置设计保障**：设计文档 §4.2.4 镜像 tag 规范是**双段式**（`agent:v1.5.0-comfyui-v0.3.77` / `agent:v1.5.0-comfyui-v0.16.4`），且**旧 v0.3.77 镜像继续保留**。这就是回退的最大保障——回退动作只是改 s.yaml 的 `image:` 字符串，秒级生效。

```yaml
# s.yaml 切回去
customContainerConfig:
  image: cap-demo-public-registry.../comfyui-agent:v1.5.0-comfyui-v0.3.77
environmentVariables:
  COMFYUI_VERSION: v0.3.77
  OSS_COMFYUI_BASE_DIR: base/comfyui/v0.3.77-gamma
```

`s deploy` → FC 平台滚动替换实例，旧请求继续跑、新请求走旧镜像。

### 3.3 棘手情况：用户已在 v0.16.4 保存了快照，要回退

**问题**：v0.3.77 和 v0.16.4 的 venv 不兼容（torch 版本差距大），快照里的 `venv.tar.zst` 跨版本加载会崩。

**本提案的设计已经考虑这点**：

- v0.16.4 的快照保存到 `${MNT_DIR}/snapshots/v0.16.4/...`
- v0.3.77 的快照保存到 `${MNT_DIR}/snapshots/v0.3.77/...`（升级后）或 `${MNT_DIR}/snapshots/...`（fallback 旧路径）
- 回退到 v0.3.77 时，agent 只看自己版本的快照目录，**自动忽略 v0.16.4 的快照**，加载用户在 v0.3.77 时代保存的最新快照

**用户视角**：

- 回退后看不到自己在 v0.16.4 期间装的新 custom node、改的工作空间——丢了
- 但用户**没丢数据**：v0.16.4 快照数据仍在 NAS 上的 `snapshots/v0.16.4/` 下，未来再次切回 v0.16.4 时还能恢复

**用户教育**：在切换版本前在 UI / 文档明确提示"切换大版本会换工作空间，原版本工作空间会保留但当前看不到"。

### 3.4 数据完整性 / 不可回退动作

需要明确**哪些动作一旦做了无法回退**，作为本提案落地的红线：

| 动作 | 可回退性 | 风险缓解 |
|---|---|---|
| 镜像 tag 切换 | ✅ 完全可回退 | s.yaml 改回去 |
| NAS 写入新版本快照 | ✅ 不破坏旧版本快照 | 双版本快照路径并存 |
| OSS `v0.16.4-gamma/` 基础包上传 | ✅ 不影响 `v0.3.77-gamma/` | 路径前缀隔离 |
| `dipper-cache` 公共 OSS 资源**删除**操作 | ❌ 不可逆 | **永远不要在回退流程里 `ossutil rm`** |
| 用户 NAS `snapshots/` 目录**删除** | ❌ 不可逆 | **永远不要在迁移脚本里 `rm`；只 `mv`** |
| 推送破坏性 commit 到 main 分支 | ⚠️ 可 revert 但有副作用 | release 严格走 git tag |
| 用户 workflow 在 v0.16.4 上 schema 改了无法在 v0.3.77 解析 | ❌ workflow JSON 单向 | UI 在保存时按当前版本打 tag；回退时提示 |

**底线**：回退**不应该删除任何数据**。新版本走自己的目录前缀，回退就是换 image tag + 改 env。这就是为什么设计文档 §4.3.2 强调路径隔离而不是原地覆盖。

### 3.5 回退演练

建议在设计文档 §8 P5 灰度之前做一次完整演练：

```bash
# 演练流程
# 1. 在测试函数部署 v0.16.4 → 跑工作流 → 保存 dev 快照
# 2. 切到 v0.3.77 镜像 → 验证：
#    - 能正常启动
#    - 能加载 v0.3.77 快照
#    - 不会误读 v0.16.4 快照
# 3. 再切回 v0.16.4 → 验证：仍能加载到第 1 步保存的 v0.16.4 快照
# 4. 多租用户并发 → 验证：v0.3.77 多租隔离不退化
```

**P5 灰度阶段每发现一个问题做一次回退演练**，确保**回退路径本身的稳定性**——回退路径不被频繁验证，真要用时往往才发现回退本身也有 bug。

#### 3.5.1 回退演练自动化

将上述手动步骤封装为可重复执行的 e2e 测试脚本，建议落到 `src/code/agent/test/e2e/test_rollback_drill.sh`：

```bash
#!/bin/bash
# 回退演练自动化脚本
# 用法: REGION=cn-hangzhou FC_FUNCTION=test-comfyui ./test_rollback_drill.sh
# 前置条件: s CLI 已配置、测试函数已存在、两个版本镜像已 push

set -euo pipefail

REGION=${REGION:-cn-hangzhou}
FC_FUNCTION=${FC_FUNCTION:-test-comfyui-rollback}
V_OLD="v0.3.77"
V_NEW="v0.16.4"
IMAGE_BASE="cap-demo-public-registry.cn-hangzhou.cr.aliyuncs.com/cap-app/image-generation-comfyui-agent"
IMAGE_TAG_PREFIX=${IMAGE_TAG_PREFIX:-v1.5.0}

echo "=== Phase 1: Deploy v0.16.4 and generate data ==="
s deploy -t s-rollback-test.yaml --vars "comfyuiVersion=${V_NEW}" --yes
sleep 10  # 等待实例启动

# 跑一个 workflow 生成输出
FUNC_URL=$(s info -t s-rollback-test.yaml 2>/dev/null | grep -o 'https://[^ ]*')
curl -sf "${FUNC_URL}/api/serverless/run" \
  -H "X-FunArt-Comfy-UserId: rollback-test-user" \
  -d @test/fixtures/benchmark_prompts/txt2img_fixed_seed.json \
  || { echo "FAIL: workflow execution on v0.16.4"; exit 1; }

# 保存快照
curl -sf "${FUNC_URL}/management/save" || true
echo "✅ Phase 1 passed: v0.16.4 data generated"

echo "=== Phase 2: Rollback to v0.3.77 ==="
s deploy -t s-rollback-test.yaml --vars "comfyuiVersion=${V_OLD}" --yes
sleep 10

# 验证能启动
STATUS=$(curl -sf "${FUNC_URL}/management/status" | jq -r '.status')
[ "$STATUS" = "RUNNING" ] || { echo "FAIL: v0.3.77 not RUNNING after rollback (got: $STATUS)"; exit 1; }

# 验证 v0.3.77 快照路径不含 v0.16.4 数据
# （通过日志检查，不应出现 "Loading snapshot from.*v0.16.4"）
echo "✅ Phase 2 passed: v0.3.77 rollback successful"

echo "=== Phase 3: Switch back to v0.16.4 ==="
s deploy -t s-rollback-test.yaml --vars "comfyuiVersion=${V_NEW}" --yes
sleep 10

STATUS=$(curl -sf "${FUNC_URL}/management/status" | jq -r '.status')
[ "$STATUS" = "RUNNING" ] || { echo "FAIL: v0.16.4 not RUNNING after re-switch"; exit 1; }
echo "✅ Phase 3 passed: v0.16.4 re-switch successful, data preserved"

echo "=== All rollback drill phases passed ==="
```

**CI 集成**：在 P5 灰度进入前作为 gate；每次 release 前自动执行一次。如果失败则阻止 release。

## 4. 可观测性

### 4.1 灰度前必须就位的指标

按优先级，最低成本起步即可上灰度：

1. **agent `/initialize` 成功率 + 时延**（按 ComfyUI 版本切片）
   - 数据源：agent 日志 / FC `x-fc-request-id` 关联
   - 告警：`/initialize` 失败率 > 1% 持续 5 分钟

2. **ComfyUI 子进程崩溃次数**（含 liveness 重启）
   - 数据源：`ComfyUIProcessManager` 日志
   - 告警：单实例 1 小时内重启 ≥ 3 次

3. **工作流执行成功率**（按 user_id + 版本双切片）
   - 数据源：`/api/serverless/run` 响应日志
   - 告警：成功率与 v0.3.77 历史基线偏差 > 5pp

4. **快照 fallback 命中率**（旧路径加载次数 = 没迁移完的存量）
   - 数据源：`snapshot_manager.py` 的 `Loading snapshot from legacy path` warning
   - 用途：判断 v0.3.77 退场时机（设计文档 §9.3）

5. **pip install 失败列表**（按插件名聚合）
   - 数据源：构建日志 + `/initialize` 阶段安装日志
   - 用途：定位 v0.16.4 兼容问题（设计文档 §7 风险表）

### 4.2 事件上报维度补充

现有的 `art_task_event` 指标体系（`services/metrics/` 模块，近期已上线）应在上报 payload 中增加 `comfyui_version` 维度字段：

```python
# 在 metrics 上报时注入版本维度
def report_task_event(event_type: str, **kwargs):
    payload = {
        'event_type': event_type,
        'comfyui_version': constants.COMFYUI_VERSION or 'unknown',  # 新增
        'instance_id': constants.INSTANCE_ID,
        **kwargs
    }
    # ... existing reporting logic
```

这样灰度期间可以在同一个看板上按版本切片对比，无需额外部署独立监控。

**已有事件类型与版本切片的关联**：

| 事件类型 | 切片维度 | 灰度用途 |
|---|---|---|
| `task_start` / `task_complete` / `task_fail` | `comfyui_version` | 对比执行成功率 |
| `initialize_start` / `initialize_complete` | `comfyui_version` | 对比冷启动时延 |
| `process_restart` | `comfyui_version` | 对比稳定性 |
| `snapshot_load` / `snapshot_save` | `comfyui_version` + `legacy_fallback` | 监控迁移进度 |

### 4.3 监控载体建议

- 阿里云 SLS（FC 日志默认入 SLS）配关键字告警 → 钉钉 / 邮件
- Grafana 看板（FunArt 内部已有的话直接复用）
- 重要：上线前必须把"按版本切片"维度加好——否则 v0.16.4 引入后无法对比基线

### 4.4 长期看板

灰度结束后保留以下长期指标：

- 各版本函数实例占比（迁移进度）
- 各版本冷启动时延对比
- 各版本工作流成功率对比

为下一次大版本升级（v0.17+）积累基线数据。
